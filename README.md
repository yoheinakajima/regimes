# regimes

An autonomous eval-improvement loop that runs natively on the published
[ActiveGraph](https://docs.activegraph.ai) runtime. The loop's entire history
— diagnosis, authored transform, gate results, keep/discard, stop decision —
is an ActiveGraph event log, not a side database.

> Status: under construction. Milestone 1 (frozen split + invariants) is in.
> See "Milestones" below.

## What it does, in one sentence

It diagnoses LongMemEval failures into regimes, has an LLM author a
score-transform to address the dominant seam-reachable regime, validates that
transform through compile → sandbox → eval-diff → promotion gates, keeps it
only if it improves a held-out slice without regressing, and stops when
remaining failures are in a regime the action space can't reach.

## Three repos, only one runs on the runtime

| Repo | Role |
|---|---|
| **regimes** (this repo) | The loop. Runs **natively on the ActiveGraph runtime**. Every step is an event. |
| **activegraph-longmemeval** ([github](https://github.com/yoheinakajima/activegraph-longmemeval)) | External system-under-test and scoring function. **Never modified.** The loop shells out to it. |
| **activegraph-behaviordrafts** ([github](https://github.com/yoheinakajima/activegraph-behaviordrafts)) | The paper that specifies the lifecycle principle (`draft → static → sandbox → semantic-diff → promotion → disable`). **Not a dependency.** The gates here are reimplemented natively for score-transforms. |

## The action space

Score-transforms injected at the documented seam in
`activegraph_det.retrieve()`, between scoring and assembly:

```python
def transform(
    scores: dict[str, float],   # turn_id -> score
    graph,
    question: str,
    question_date: str,
) -> dict[str, float]:           # new score dict over the same turn IDs
    ...
```

Transforms may re-weight, blend, penalize, or filter scores. They **cannot**:
- edit `assemble()` internals,
- touch the filesystem / network,
- mutate the graph,
- reach the scorer or the dataset.

The static-analysis gate enforces this; it is the entire safety model.

## Held-out discipline (READ THIS)

The loop refuses to start without `config/split.json`, a frozen
OPTIMIZE/CONFIRM partition.

- **OPTIMIZE** (50 question_ids, stratified by `(question_type, is_abs)`,
  seed=42) is the only set used for diagnosis, sandbox, and eval-diff.
  Transforms are optimized and selected on OPTIMIZE.
- **CONFIRM** (100 question_ids, same stratification rule, disjoint from
  OPTIMIZE) is touched **once per promotion** and only for reporting.

At startup the loop asserts `OPTIMIZE ∩ CONFIRM = ∅` and raises
`activegraph.ConfigurationError` (per ActiveGraph's failure model — this is a
caller-fixable construction error, not a logged event) if it doesn't hold.

**Reporting an OPTIMIZE-tuned number as the result would be overfitting.**
The headline number is the CONFIRM number, after a promotion has been made.

### Why a synthetic fixture?

The cloned LME repo doesn't ship `longmemeval_s_cleaned.json`; it's pulled
from HuggingFace. In this build environment HuggingFace is unreachable, so
`scripts/build_split.py` runs against `fixtures/synthetic_lme.json` — a
200-question LME-shaped fixture generated by `scripts/build_fixture.py`
(deterministic, seed=42, byte-identical on re-run, committed). The same
generator produces a real split once `data/longmemeval_s_cleaned.json` is
present:

```bash
python scripts/build_split.py --source data/longmemeval_s_cleaned.json
```

Both paths go through the same code; the loop never knows which source it
came from beyond what `split.json` records.

## Failure model

Follows ActiveGraph's. Caller-fixable construction errors (bad config,
overlapping split, missing LME checkout when real-eval requested) **raise**.
Everything that happens during a loop run (a transform crashing in sandbox,
an eval failing, a gate rejecting) is a **logged event** with the error
carried in the payload, and the loop continues.
